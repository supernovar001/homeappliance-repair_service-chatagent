워시케어 서비스(기획서 v1.0)를 만들면서 생긴 **확인할 점**과 **특이사항**을 이어서 기록합니다.
특이사항은 나중에 설명하기 쉽도록 "문제 → 원인 → 해결 → 근거(숫자)" 순서로 씁니다.

- 브랜치: `feature/washcare-service` (단계마다 커밋, `main`에 합치면 Railway가 배포)

## 3. 특이사항 기록

### I-01 기준 평가가 밤새 12시간 멈춤 (2026-10-30)
- **문제**: 변경 전 기준을 잡는 holdout 평가가 아침까지 끝나지 않았습니다. 로그에는 아무것도 없었습니다.
- **원인**:
  - 노트북이 잠든 사이 OpenAI 연결이 끊겼는데, 변경 전 `app.py`에는 응답 제한 시간이 없어 계속 기다렸습니다.
  - 출력이 버퍼에 쌓여 있어 진행 상황도 보이지 않았습니다.
- **근거**: 12시간 동안 CPU를 13초만 썼습니다(`ps -o etime,time`).
- **해결**:
  - `ChatOpenAI(timeout=OPENAI_TIMEOUT)`를 추가했습니다(기본 60초).
  - 평가는 `python -u`로 돌려 진행 상황이 바로 로그에 찍히게 했습니다.
  - 서비스에서는 이 제한 시간이 멈춘 호출이 작업 슬롯(동시 2개)을 붙잡는 것을 막습니다. 작업 전체에도 240초 제한을 따로 둡니다.

### I-02 메모리 8GB에서 스왑이 가득 차 평가가 기어감 (2026-10-30)
- **문제**: 다시 돌린 평가가 문항당 1분 넘게 걸리다가 23번째 문항에서 사실상 멈췄습니다.
- **원인**: Docker Desktop 가상 머신이 4GB를 예약한 상태에서 재정렬 모델(bge-reranker-v2-m3)이 약 2GB를 썼습니다.
- **근거**: 스왑 사용량 10.7GB/12GB였고, 평가 프로세스의 실제 메모리(RSS)는 2MB였습니다. 거의 통째로 스왑에 밀려나 있었습니다.
- **해결**: 평가하는 동안 Docker를 종료했습니다. 그러자 변경 후 holdout 50문항이 약 20분 만에 끝났습니다.
- **배운 점**: 같은 모델을 쓰는 배포 서버의 메모리를 4GB 이상으로 권하는 근거입니다. 로그가 멈추면 먼저 CPU 시간과 스왑을 봅니다.

### I-03 capstone 평가가 Mac GPU 오류로 종료 (2026-10-30)
- **문제**: `src/capstone_eval.py`가 결과 없이 끝났습니다.
  - 오류: `failed assertion 'A command encoder is already encoding to this command buffer'`
- **원인**: 이 스크립트는 질문 5개를 스레드 5개로 동시에 돌립니다. Mac GPU(MPS)에서 재정렬 모델을 동시에 부르면 프로세스가 죽습니다.
  - 서비스도 상담 작업을 스레드 2개로 돌리므로 같은 위험이 있었습니다.
- **해결**: `app.py`에 `RERANK_LOCK`을 두어 재정렬 호출만 한 번에 하나씩 합니다. 검색 결과는 같고, OpenAI 호출은 지금처럼 동시에 나갑니다.
  - 기준(변경 전) 평가는 코드를 고치지 않고, 실행할 때만 같은 잠금을 씌우는 래퍼로 돌려 비교 조건을 맞췄습니다.

### I-04 자유 입력으로 알린 점검 결과를 모델이 체크리스트에 담지 못함 (2026-10-30)
- **문제**: 고객이 "배수 호스 펴 놨는데 그래도 OE가 떠요"라고 써도 체크리스트의 배수 호스 항목이 `미확인`으로 남았습니다.
- **원인**: gpt-4o-mini가 구조화 출력의 `customer_report`를 안정적으로 채우지 못했습니다.
- **근거**: 두 가지 방식으로 시도해 두 번 모두 실패했습니다.
  - 규칙을 시스템 프롬프트에 둔 경우: 같은 key로 항목을 넣었지만 결과를 채우지 않았습니다.
  - 점검 현황 메시지에 예시와 함께 둔 경우: 항목 자체를 뺐습니다.
- **해결**:
  - 점검 결과는 답변 카드의 "점검 결과 알려주기" 버튼으로 받는 것을 주 경로로 정했습니다(묶음 API, 상태값을 서버가 그대로 저장).
  - 자유 입력은 근거 발화가 실제 고객 발화와 맞을 때만 보조로 반영합니다.
- **추가 관찰**: 체크리스트를 별도 호출로 옮긴 뒤(I-08)에도 2회 중 1회는 놓쳤습니다. 나머지 1회는 결과를 "서비스 센터 문의" 항목에 잘못 붙였습니다.
  - 근거 발화는 실제 고객 말이라 검증을 통과해 버리므로, 잘못 붙는 쪽이 놓치는 쪽보다 위험합니다.
  - 그래서 고객 수행 기록은 고객이 직접 하는 점검(`self_check`) 항목에만 인정하도록 막았습니다.
- **배운 점**: LLM에 맡길 일(안내문 작성)과 UI·코드로 확정할 일(점검 상태)을 나눴습니다. 검증은 "근거가 진짜인가"뿐 아니라 "근거를 올바른 대상에 붙였는가"도 봐야 합니다.

### I-05 체크리스트 key 정규화 버그 (2026-10-30)
- **문제**: 모델이 key를 `Drain Hose`처럼 띄어 쓰면 `drainhose`로 바뀌었습니다. 그래서 `drain_hose`와 같은 항목인데 중복으로 걸러지지 않았습니다.
- **발견**: OpenAI 없이 돌린 검사 스크립트에서 찾았습니다.
- **해결**: 공백과 하이픈을 밑줄로 바꾼 뒤 허용 문자만 남깁니다.

### I-06 답변 1건에 150~230초 → 실제로는 15~19초 (2026-10-30)
- **관찰**: 처음 실제 AI로 OE 질문을 돌렸을 때 첫 답변이 229.6초, 후속 답변이 151.8초 걸렸습니다. 작업 제한 시간 240초에 가까웠습니다.
- **원인**: 기준 평가가 같은 Mac에서 함께 돌았고, 메모리가 스왑에 밀린 상태였습니다(I-02).
- **재측정**: 다른 작업이 없는 상태에서 OE·UE 예시 질문 3건을 쟀습니다. 3건 모두 재생성이 1회 있었습니다.

  | 구간 | 시간 |
  |---|---|
  | 전체 | 14.6~18.5초 |
  | 범위 분류(LLM) | 1.6~3.8초 |
  | 검색과 재정렬 | 5.1~6.6초 |
  | 답변 작성(LLM) | 2.0~3.2초 |
  | 재생성(LLM) | 2.6~3.2초 |
  | 체크리스트 별도 호출(LLM) | 1.9~2.8초 |

  - 진행 단계 이벤트는 각 단계가 시작한 시각이라, 구간 시간은 다음 단계 시작 시각과의 차이로 계산했습니다.
  - 가장 긴 구간은 검색과 재정렬(Mac GPU 기준)입니다.

  - 재정렬 모델 로딩은 서버 시작 때 한 번 17~30초 걸립니다. `WasherEngine.load()`가 미리 불러 둡니다.
- **남은 확인**: Railway는 GPU 없이 CPU로 재정렬하므로 검색 구간이 더 길 수 있습니다. 배포 후 관리자 화면의 응답시간 P95로 확인합니다.

### I-07 `app.py`를 모듈로 나눌 수 없음 (2026-10-29, 설계 제약)
- **문제**: 서비스를 붙이려면 AI 코드를 모듈로 나누는 것이 자연스러워 보였습니다.
- **원인**: 평가 스크립트들이 `app.retriever = app.build_retriever(mode)`처럼 모듈 전역 변수를 바꿔 검색 방식을 비교합니다. 모듈을 나누면 오류 없이 **잘못된 결과**가 나옵니다.
- **해결**: `app.py`는 그대로 두고, 백엔드는 `backend/engine.py`에서 지연 import합니다.
  - 새 입력(기억·점검 현황·진행 이벤트)은 값이 있을 때만 프롬프트에 영향을 줍니다. 그래서 평가 입력은 이전과 같습니다.

### I-08 체크리스트를 상담 출력에 함께 넣자 안내문의 원인이 줄어듦 (2026-10-30)
- **문제**: 1단계 회귀 평가에서 원인 포함률만 떨어졌습니다. 나머지 지표(범위·상담 분류, 인용, 근거 검색, 실행 오류)는 기준과 같았습니다.
- **근거**: 원인 포함률이 63/63(14문항 모두 포함)에서 62/69(15문항 중 10문항만 모두 포함)로 내려갔습니다.
  - 빠진 문항은 모두 원인이 6개인 증상(UE 2문항, OE 3문항)이었습니다.
- **원인**: 상담 출력(JSON)에 `checklist`(최대 5개)를 함께 넣자, 모델이 안내문(`guidance`)까지 5개 안쪽으로 줄였습니다.
  - "5개 제한 때문에 안내문을 줄이지 말라"는 규칙을 더해도 62/69, 전부 포함 9/15로 그대로였습니다. 규칙 문구의 문제가 아니라 출력 구조의 문제였습니다.
- **해결**: 상담 체인은 변경 전과 똑같이 되돌렸습니다(시스템 프롬프트 동일 여부를 코드로 확인).
  - 체크리스트와 증상 요약은 완성된 안내문을 입력으로 받는 별도 호출(`checklist_chain`)로 만듭니다.
  - 그 결과 원인 검사 대상 15문항에서 67/69(전부 포함 13/15)가 나왔습니다.
- **비용**: 답변마다 gpt-4o-mini 호출이 1번 늘어납니다. 이 호출이 실패해도 답변은 나가고 체크리스트만 비웁니다.
- **배운 점**:
  - 구조화 출력에 필드를 더하는 것은 "공짜"가 아닙니다. 같은 호출의 다른 필드 품질에 영향을 줍니다.
  - 회귀 평가가 없었다면 서버가 빠진 원인을 설명서 문장으로 덧붙이는 보완 장치 때문에 겉으로는 드러나지 않았을 문제입니다.

### I-09 기준값 63/63은 한 번 운 좋게 나온 값이었음 (2026-10-30)
- **문제**: 체크리스트를 별도 호출로 옮긴 뒤(I-08)에도 원인 포함률이 60/63(전부 포함 11/14)이었습니다. 기준 63/63보다 낮았습니다.
  - 그런데 이때 상담 체인의 입력은 변경 전과 완전히 같았습니다.
- **확인**: 원인 검사 대상 14문항을 변경 전 코드로 다시 돌렸습니다.

  | 측정 | 원인 포함률 | 전부 포함 |
  |---|---|---|
  | 변경 전 코드, 처음 기준 | 63/63 | 14/14 |
  | 변경 전 코드, 재측정 1회 | 58/63 | 9/14 |
  | 변경 전 코드, 재측정 2회 | 59/63 | 11/14 |
  | 변경 후 코드, 전체 holdout | 60/63 | 11/14 |
  | 변경 후 코드, 재측정 | 60/63 | 11/14 |

  - 빠지는 문항도 매번 달랐습니다(H05·H06·H07·H09·H24·H46 중 일부).
- **원인**: gpt-4o-mini는 temperature 0이어도 응답이 완전히 고정되지 않습니다. 원인을 6개씩 나열해야 하는 문항에서 한두 개를 빠뜨리는 일이 실행마다 다르게 일어납니다.
- **판단**: 변경 후 값은 변경 전 코드의 편차 범위(58~63) 안에 있으므로 회귀가 아닙니다. 상담 분류 45 대 46(H49 라벨 하나)도 같은 이유로 봅니다.
  - 반대로 I-08의 1차 구조(62/69, 전부 포함 10/15)는 빠진 문항이 원인이 6개인 증상에만 몰려 있었고, 문구를 고쳐도 재현됐으므로 실제 회귀로 봤습니다.
- **배운 점**:
  - 평가는 한 번 돌린 값으로 기준을 잡으면 안 됩니다. 같은 코드를 2~3번 돌려 편차 범위를 먼저 재고, 그 범위를 벗어날 때만 회귀로 판단합니다.
